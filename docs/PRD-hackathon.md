\# TwinHands-AI — Product Requirements Document (Hackathon)



\*\*Document status:\*\* Hackathon project requirements  

\*\*Product:\*\* TwinHands-AI  

\*\*Version:\*\* 1.0  

\*\*Purpose:\*\* Define functional requirements, safety boundaries, and acceptance criteria for the simulation-first demonstration.



\## 1. Product objective



Build a simulation-first application that transforms a natural-language table-preparation request into a validated task plan, executes the task through the existing deterministic simulation pipeline, and independently verifies the resulting simulator state.



The system must clearly distinguish between:

\- \*\*Model proposal:\*\* A plan generated by the language model.

\- \*\*Validated plan:\*\* A plan that has passed schema, type, and business-rule validation.

\- \*\*Simulation execution:\*\* Actions performed by the existing deterministic simulation pipeline.

\- \*\*Verified result:\*\* An outcome supported by actual simulator state and recorded evidence.



A model response alone must never be treated as proof that a task has been completed successfully.



\## 2. Target users



1\. \*\*Institutional kitchen and canteen operations teams\*\* evaluating potential automation workflows.

2\. \*\*Robotics engineers\*\* testing natural-language task planning and structured plan generation.

3\. \*\*Automation integrators\*\* evaluating workflow feasibility before physical deployment.

4\. \*\*Hackathon judges\*\* reproducing the demonstration and assessing its technical implementation.



\## 3. Scope



\### In scope



\- Natural-language task requests.

\- Nemotron inference through Nebius Token Factory.

\- Structured task-plan generation.

\- Server-side response validation.

\- Integration with the existing deterministic planner and simulator.

\- Safety and layout validation before execution.

\- Independent verification of the final simulated state.

\- Evidence recording and a user-visible status summary.

\- Reproducible setup, testing, and demonstration instructions.



\### Out of scope



\- Unsupervised operation of physical robots.

\- Complete kitchen automation.

\- Production safety certification.

\- Medical or laboratory deployment.

\- Claims of guaranteed collision avoidance.

\- Claims of guaranteed commercial return on investment.



\## 4. Functional requirements



| ID | Requirement | Acceptance criteria |

|---|---|---|

| FR-01 | Accept natural-language requests | Empty, whitespace-only, or oversized requests are rejected with a clear error. |

| FR-02 | Call Nemotron through Nebius | A real runtime inference request succeeds when valid credentials and provider access are available. |

| FR-03 | Produce a structured task plan | The response contains all required fields with the expected data types and permitted values. |

| FR-04 | Validate the model response | Malformed JSON, invalid counts, missing fields, and invalid item types are rejected. |

| FR-05 | Connect to deterministic planning | Only plans that pass validation are passed to the existing deterministic planner. |

| FR-06 | Enforce safety constraints | Invalid or unsafe layouts are rejected before simulation execution begins. |

| FR-07 | Verify the final state | Success is reported only when the simulator's actual final state satisfies the defined verification conditions. |

| FR-08 | Record evidence | The system records execution status, model identifier, latency, and verification results without storing secrets. |

| FR-09 | Handle failures | Missing credentials, provider errors, timeouts, invalid model output, and simulation failures produce visible, actionable error states. |



\## 5. Non-functional requirements



\### Security

\- API keys and provider credentials remain server-side.

\- Credentials must not appear in browser responses, client-side bundles, logs, or committed configuration files.

\- Secret values must be redacted from error messages and evidence records.

\- Environment configuration must be documented without including real credentials.



\### Reliability and bounded execution

\- Input length and accepted numeric ranges must be bounded.

\- Provider requests must have a configurable timeout.

\- Malformed or invalid model output must fail safely.

\- A failed validation or safety check must not start the simulation.

\- Errors must not be silently converted into successful results.



\### Reproducibility

\- Document required software, environment variables, installation, startup, and testing commands.

\- Provide repeatable test cases for success, invalid input, provider failure, and safety rejection.

\- Document the simulator assumptions and verification criteria.



\### Observability

\- Record useful execution metadata, including status, model identifier, elapsed time, and verification outcome.

\- Use consistent status categories so a judge can distinguish request rejection, planning failure, simulation failure, and verified completion.



\### Evidence integrity

\- Keep model output, validated plans, simulator results, and verification evidence logically distinct.

\- Never infer successful execution merely from a successful HTTP response or a well-formed model response.

\- Report only measurements obtained through a documented test procedure.



\## 6. Proposed request-to-verification workflow



1\. Receive a natural-language request.

2\. Validate request presence, length, and supported parameters.

3\. Call Nemotron through Nebius Token Factory.

4\. Parse the model response and validate the structured plan.

5\. Pass the validated plan to the deterministic planner.

6\. Validate the proposed layout against the application's implemented safety constraints.

7\. Reject execution if a required validation fails.

8\. Run the existing deterministic simulation.

9\. Inspect the actual simulator state using independent verification logic.

10\. Record the execution status, model identifier, timing, and verification evidence.

11\. Display the result and any failure reason to the user.



\## 7. Safety and failure handling



The system must fail closed at validation and execution boundaries.



| Scenario | Expected behavior |

|---|---|

| Empty request | Reject before provider inference. |

| Oversized request | Reject before provider inference. |

| Missing API key | Report a configuration error without exposing credentials. |

| Provider timeout or error | Report planning failure; do not claim task completion. |

| Invalid JSON | Reject the model response. |

| Invalid count or item type | Reject the plan before deterministic planning. |

| Unsafe layout | Block simulation execution. |

| Simulation exception | Report execution failure and preserve available diagnostic evidence. |

| Verification failure | Report an unverified or failed outcome, not success. |

| Successful verification | Report completion only when the defined simulator-state checks pass. |



\## 8. Evidence and metrics



For each test run, record the applicable fields:



\- Run identifier.

\- Timestamp.

\- Sanitized request or request identifier.

\- Model/provider identifier.

\- Inference latency.

\- Validation status.

\- Safety-validation status.

\- Simulation execution status.

\- Verification status and evidence.

\- Error category, if applicable.



Do not record API keys or other secrets. Avoid retaining unnecessary sensitive request content.



\### Measurement rules



\- \*\*Latency:\*\* Measure elapsed time with a defined start and end point. State whether provider inference, simulation, and verification are included.

\- \*\*Success rate:\*\* Report successful runs divided by the number of eligible test runs, with the sample size and test conditions.

\- \*\*Validation rejection:\*\* Report the number of invalid test cases rejected and the total number tested.

\- \*\*Verification:\*\* Document the simulator-state predicates used to determine success.



Do not publish accuracy percentages, reliability claims, or performance results until they have been measured and reproducibly documented.



\## 9. Acceptance test checklist



\- \[ ] A valid natural-language request reaches the planning stage.

\- \[ ] A real Nebius-hosted Nemotron inference request succeeds.

\- \[ ] The structured plan passes schema and business-rule validation.

\- \[ ] Empty and oversized requests are rejected.

\- \[ ] Malformed JSON and invalid item types are rejected.

\- \[ ] Invalid numeric counts are rejected.

\- \[ ] A safety-rejected layout cannot start simulation.

\- \[ ] A valid plan reaches the deterministic simulation pipeline.

\- \[ ] Verification uses actual simulator-state evidence.

\- \[ ] Provider and simulation failures are visible.

\- \[ ] Evidence records contain no secrets.

\- \[ ] Setup and test instructions can be followed from the repository.



Mark a test as passed only after executing it and recording the result.



\## 10. Hackathon demonstration



The demonstration should show three distinct paths:



1\. \*\*Valid workflow:\*\* Request → Nemotron proposal → validation → deterministic simulation → independent verification.

2\. \*\*Invalid input or safety rejection:\*\* Show the rejection and confirm that simulation did not start.

3\. \*\*Failure handling:\*\* Demonstrate a recoverable configuration, provider, or simulation error where practical.



Identify the pre-existing code and the changes made for the hackathon. Clearly disclose any mocked components and never present a mock response as real provider inference or real simulator evidence.



\## 11. Assumptions and dependencies



\- The repository contains an existing deterministic simulation pipeline.

\- The application can be configured to call Nebius Token Factory.

\- The selected Nemotron model is available to the configured provider account.

\- The implementation provides, or will add, a structured plan schema and final-state verification checks.

\- Actual route names, model identifiers, accepted ranges, and verification predicates must be confirmed against the implemented source code.



\## 12. Definition of done



The hackathon implementation is ready for evaluation when the documented end-to-end workflow works, invalid and unsafe requests are blocked, completion depends on actual simulator verification, failures are observable, and a judge can reproduce the documented tests without access to embedded secrets.



\*\*Product principle:\*\* A generated plan is a proposal; only validated execution and verified simulator evidence can support a completion claim.
